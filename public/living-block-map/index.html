What is WordPress Core AI?

WordPress Core AI is a set of open building blocks that let WordPress use AI services and let outside assistants work with WordPress—without tying either direction to one provider.

Core API · 6.9

Abilities API

Where
Inside WordPress
Core status
WordPress Core API · since 6.9

What it is

Abilities are the list of things this site can do. Each one declares its inputs, its outputs, who is allowed to run it, and what happens when it runs.

More details below ↓

Under the hood

How it connects

Input→ Permission→ Run→ Typed output

The PHP API landed in WordPress 6.9. WordPress 7.0 added a client-side counterpart for editor actions such as navigation and block insertion. A public default for client exposure, filtering in wp_get_abilities(), and filters around execution arrive in WordPress 7.1 on August 19, 2026. This exhibit runs a 7.1 release candidate, so the Anatomy panel describes the version you are looking at.

Reached from both directions. An outside assistant is not the only caller. A request made by the AI Client inside WordPress can name registered abilities a model is allowed to call, and every one of those calls still passes the same permission check.

Open the canonical project page https://developer.wordpress.org/apis/abilities-api/ Keep exploring on your own device.

One registration, annotated

Awp_register_ability( 'bookings/get-availability', [

B 'label' => 'Get availability',

'description' => 'Open slots in a range.',

'category' => 'bookings',

'input_schema' => $schema,

C 'permission_callback' => $can_book,

'execute_callback' => $handler,

'meta' => [

D 'public' => true,

E 'annotations' => [ 'readonly' => true ],

],

] );

  • ATwo segments, lowercase. The name is public API. Renaming it later breaks every caller.
  • BThis is the part an agent reads. It picks the ability from these two lines alone. If the description needs an “and”, it is two abilities.
  • CChecked on every call. An editor button, a REST client and an outside assistant all pass through the same gate.
  • DOne flag, every client. New in 7.1. Public says this ability is meant for the outside — REST, MCP adapters, agents. Leave it out and it stays private; a channel can still be turned off on its own.
  • EHints to a client — and the verb core requires. Read-only tells a client this ability changes nothing; over REST it also makes GET the only way to call it, and the wrong method is refused. What annotations never decide is who may call it.

Validation is not sanitization. The schema checks types and required fields. It does not clean input, and it does not fill in the defaults you wrote. Whatever arrives is raw.

Three gates, one call

Assistant→ Transport→ Meta-tool→ Your callback
  1. The endpoint lets you inThe adapter’s default transport check is only whether someone is logged in. On a stock install a subscriber clears this gate.
  2. The tool lets you askOn the default server abilities are not listed one by one. Three adapter tools stand in front of them — discover, inspect, execute — and each carries its own capability.
  3. The ability decidesOnly the last gate sees what is actually being asked — which booking, which date, on whose behalf. This is the one you write.

All three must pass. The first two default to little more than “someone is logged in”. A permission check only ever tried as an administrator has not been tested.

An assistant acts as a real logged-in user. An ability that is too generous hands an outside service that user’s reach. Exposure is not authorization: public decides what a client may see, never what it may run.

Core API · 7.0

AI Client

Where
Inside WordPress
Core status
WordPress Core API · since 7.0

What it is

A plugin asks for a capability and the kind of result it needs. The AI Client routes through an installed provider plugin to a compatible external service; Connectors supplies that plugin’s configuration and credentials.

More details below ↓

Under the hood

How it connects

Capability request → AI Client → Model resolution → Provider plugin → Normalized result

A WordPress wrapper around the provider-agnostic PHP AI Client, which handles provider communication, model selection, and normalized results. Consuming plugins never integrate a provider directly. A named model is a preference, not a requirement: if none of the preferred ones are configured, the request falls back to the first available model that can do the job. Core’s client is PHP only — the JavaScript prompt builder lives outside Core and is administrator-only, because it can send any prompt to any configured provider, so a feature exposes its own REST endpoint instead. Check support before showing any AI interface: the check is free and makes no network call, and a 7.0 site may have no provider configured at all.

Not every request returns a result

A failure arrives as a WordPress error rather than an exception, and a site can block prompts outright — the support check then reports false and the feature hides itself. Design for the empty answer as well as the good one.

Calling back into WordPress

A request can name registered abilities the model is allowed to call. When it calls one, WordPress runs that ability — permission check and all — and folds the result back into the same request. This is where the two halves of the map meet: WordPress asking AI for something can end with WordPress doing the work itself.

Core API · 7.0

Connectors

Where
Inside WordPress
Core status
WordPress Core API · since 7.0

What it is

Where a site owner installs provider plugins, supplies credentials, and sees connection status — one setup shared by every plugin that needs it. It supports the request path; it is not the request executor.

More details below ↓

Under the hood

Connection states

Available Needs plugin Needs credentials Connected

Providers

Provider plugins register with the AI Client. Connectors auto-discovers them, and one button installs and activates the plugin before asking for its key. The map stays vendor-neutral: no provider owns a position on the canvas.

Introduced in WordPress 7.0 as a standardized framework for registering and managing connections to external services. AI providers are the first users of it, not the only intended ones — the framework is built for outside connections generally. A saved key is not always the key in use: an environment variable is read first, then a wp-config constant, then the value stored here in the database, where it sits unencrypted by default — so on a managed host the platform’s own key can quietly outrank the one typed into this screen.

WordPress plugin · not in Core

MCP Adapter

Where
WordPress boundary
Core status
WordPress plugin · not in Core

What it is

Translation at the edge of the site. It exposes the abilities their authors marked public to authorized outside assistants — as MCP resources and prompts automatically, and as individual tools on a custom server — then translates their calls back into WordPress work. On the default server abilities are reached through three adapter tools rather than listed one by one.

More details below ↓

Under the hood

How it connects

MCP tool call → Transport check → Meta-tool → Permission → Run

An official WordPress package installed as a plugin, not part of Core: HTTP and STDIO transports, configurable servers, validation, permission checks, error handling, and observability. The default server supports multiple MCP protocol versions; its HTTP transport implements MCP 2025-11-25. Today it answers calls; it does not make them. It does not create the underlying action, and it is not the model — WordPress still owns execution.

Early benchmark

WP-Bench

Where
Evaluation · separate from live requests
Core status
Core AI project · not in Core

What it is

A test bench, not part of any live request. It measures whether the code an agent writes for WordPress actually runs.

More details below ↓

Under the hood

How it connects

Task → Sandbox → Static and runtime checks → Evidence

One suite, one dimension: the wp-core-v1 code generation tasks, graded by runtime assertions in a real WordPress environment. WordPress itself runs the assertions. Static checks sit alongside as a diagnostic — a missing pattern costs nothing, but a forbidden one fails the test outright. Passing is all-or-nothing: a partially correct result still fails. Run --check-reference-solution first to prove the grader accepts the canonical solution, then --check-exploits to prove trivial stubs fail.

A program outside WordPress — a chat assistant, an editor, an agent — that speaks MCP. It holds no privileges of its own: it signs in as a WordPress user it was given credentials for, and never reaches further than that user can.

WordPress plugin

AI provider plugin

Where
Inside WordPress
Core status
Provider plugin · not in Core

What it is

A provider-specific integration installed as a WordPress plugin. It speaks one external service’s protocol using the credentials Connectors resolved for it, and it is what turns that service into something a site owner can choose.

How it connects

Registers its models → Appears in Connectors → Receives routed requests

Under the hood

Registration is what makes the Connectors card exist: the plugin declares itself and each model’s capabilities to the AI Client, and Connectors reads that registry to build the Settings screen. A declared capability is a promise — the Client routes matching requests to whatever the plugin claims it can do. Credentials are read from an environment variable, then a PHP constant, then whatever was saved in Connectors.

The run loop

Five stages, in the same three bands as the map. Open a stage for its details. Nothing here touches a live site.

AI model · outside WordPress

Stage 01 of 05

Stage 01 · outside the site

One task, one message

A prompt and its requirements, handed to the model as a single message. Every model gets exactly the same text, so a difference in the result is a difference in the model.

A baseline run sends no system prompt either — the model gets the task text and nothing else. Comparing a skill is the exception: the skill goes in as a system message, and every model runs the same task both ways.

promptWrite the code that does this. One task, one message.

requirementsNamed functions and hooks, and the shape of what they return.

never sentNo conversation, no follow-up, no hint about the assertions. No system prompt either, unless the run is measuring a skill.

Stage 02 · outside the site

Whatever the model wrote

The harness takes the reply and parses the PHP out of it. If the answer does not parse, that is the answer — nothing is repaired on the way in.

Only a reply that opens or closes with a code fence gets unwrapped. A model that says hello first has its greeting run as PHP — a scoring artifact that belongs to the harness, not the model.

replyWhatever the model wrote, in full.

parsed outThe PHP the harness could find in it.

not repairedNothing is patched and nothing is retried before it runs.

Stage 03 · inside WordPress

A real WordPress, thrown away after

The code runs inside a WordPress that exists only for this one test. That is what makes the result a fact about WordPress rather than a fact about a fixture.

Sandbox means the container, not the language. The submitted code is evaluated inside that WordPress with nothing sandboxing it further — safe to run because the whole install is disposable.

the installA real WordPress 7.0, created for this one test.

the runSetup, then the model’s code, then the assertions, then teardown.

afterwardsThe install is thrown away. No live site is ever involved.

Stage 04 · inside WordPress

WordPress is the grader

The assertions are WordPress code inspecting WordPress state — not a model judging another model’s answer. Passing is all or nothing.

Two of three assertions is a fail. The harness still records the fraction — 0.67 is a real number in the results, and it still earns nothing.

3 of 3Pass.

2 of 3Fail. There is no partial credit.

static analysisA diagnostic only — unless the code trips a forbidden pattern, which fails the test outright.

Stage 05 · back in the harness

Pass or fail. Never a percentage

Three inputs go through the same verifier, and each one proves a different thing. Run them in this order.

A broken grader still reports a number. If the sandbox never started, every test scores zero and the run still exits clean — which looks exactly like a model that failed everything.

--check-reference-solutionProves the grader works. The canonical solution goes in, no model is called. Run it first: if this fails, no other number means anything.

a normal runProves the model works. What the model actually wrote goes in — the only number worth reporting, and only once the other two hold.

--check-exploitsProves the test is specified. An empty function goes in, then a bare return. Every one must fail — a test a stub can pass was checking a fixture, not WordPress.
